## 数据更新角标（全站右上角）

导航栏最右侧固定一个胶囊角标，显示本页正在使用的数据版本：

- **文字**：`数据更新 11/04 15:10 · 1 分钟前`
- **圆点颜色**：金色 = 36 小时内 / 灰色 = 超过 36 小时 / 红色 = 超过 7 天未更新
- **悬停**：展开浮层，显示数据生成时间（精确到秒）、数据截止日、覆盖场次、源表名
- **点击**：绕过浏览器与 CDN 缓存强制重新加载，用来确认线上是不是最新版本

判断方式：重新推过数据后，如果角标时间没变，说明看的还是缓存，点一下角标即可；
若时间变了但数字没变，说明源表数据本身没更新。

## 日期筛选（全站统一）

页面顶部固定一条筛选条，四个页面共用同一套逻辑：

- **预设**：近 7 天 / 近 30 天 / 近 90 天 / 本月 / 上月 / 近半年 / 全部
- **自定义**：起止日期选择器，自动纠正「起 > 止」，并限制在数据可选范围内
- **对比期**：自动取紧邻的等长区间，KPI 上的涨跌与明细表的环比都基于它；若已顶到数据起点，会明确显示「无对比期」，不伪造对比
- **联动范围**：KPI、趋势、班次、主播、漏斗、品类、单品全部跟随
- **链接可分享**：区间会写进 URL（`?f=2026-10-04&t=2026-11-02`），发出去对方打开看到同一视图
- **粒度自适应**：区间 ≤45 天按日、≤150 天按周、更长按月。日粒度用柱状（成交）+ 折线（净销售），更长的粒度用双折线
- **末尾不完整周期自动剔除**：月末/周末只有几天数据时不出现在趋势图里，避免被读成断崖式下跌；明细表中仍保留该行并标注「不完整」

## 主播页筛选（主播表现专用）

在日期筛选条之下另有一条页内筛选，只作用于主播页：

| 维度 | 交互 | 说明 |
|---|---|---|
| **主播** | 多选，点名字切换；「全部」一键还原 | 每个 chip 标注该主播在当前日期区间内的场次数；颜色与卡片、散点、矩阵一致 |
| **活动场次** | 多选，点名字切换；「不限」一键还原 | 名称取自「天猫活动节奏」官方表的**具体活动名**（双11 / 超级88 / 618 / 国庆狂欢 …），每个 chip 标注该节奏在当前区间的场次数；超过 10 个折叠为「更多 +N」 |

筛选会同时作用于：主播卡片、效率对比矩阵、单场分布、主播×班次、组合明细、自动结论。「全员」列在筛选后自动改称「已选合计」，不会把部分人的数字冒充全量。

**活动名称怎么来的**：源表 V1 新增了「天猫活动节奏」逐日日历（2025-01-01 ~ 2026-11-30，699 天，含日期 / 节奏 / 类型 / 直播间机制），`build_data.py` 按日期把每场直播挂到官方节奏上，**1,795 场全部匹配，0 场落空**。

名称只做归一、不改语义：

- 剔除附在名称后的券信息备注（「无消费券」「有消费券」「无消费券和限时红包」）和换行
- 去掉官方名的「天猫」前缀
- 同一活动的跨年写法合并（`618狂欢节`→`618`、`天猫新势力周`/`8月新势力周`→`新势力周`、`天猫38焕新周`→`38焕新周`），映射表在 `build_data.py` 的 `RHYTHM_ALIAS`
- 分波次/分阶段的名称保持独立（`年货节第一波`~`第四波`、`618抢先购`、`618大促520告白季`、`9月新风潮` vs `11月新风潮`），因为它们是不同活动期，合并会掩盖节奏差异

全量 32 个节奏名，场次 top：日销 425 / 618 221 / 双11 152 / 超级88 130 / 新势力周 67 / 七夕+超级88 66 / 国庆狂欢 58 / 年货节第三波 58。官方类型分布：**活动 1,228 场 / 日销 567 场**。

排班覆盖期（2026-10-01 ~ 11-02，131 场）的真实节奏是：**双11 55 / 日销 28 / 国庆狂欢 24 / 10月超级88 24**（其中活动 79 场、日销 52 场；有主播的 98 场为双11 41 / 日销 21 / 国庆狂欢 18 / 10月超级88 18），不再像旧版那样全被归成一类。另有 19 场落在「直播间机制 = 下单加赠箱套」的日期上（10-20、10-21、10-31、11-01、11-02 五天）。

## 销售目标达成（分日 × 班次）

源表「天猫排班及目标表」H~K 列给了**每天四个班次（数字人 / 早 / 中 / 晚）各自的销售目标**，`build_data.py` 读成 `targets: {日期: [数字人, 早, 中, 晚]}`。

页面上分两处体现：

| 位置 | 内容 |
|---|---|
| 班次分析 · 01 班次卡片 | 每张卡底部「目标 xx万元 · N 天 / 达成 xx%」+ 进度条 |
| 班次分析 · 03 销售目标达成 | 累计目标 vs 累计实际双线图；分日 × 四班次达成率表（胶囊色阶）；合计行给出「实际 / 目标」 |
| 总览 · 04 区间明细 | 新增「目标达成」列，按当前粒度（日/周/月）汇总，悬停看实际值与目标值 |

**口径（这几条决定了数字对不对）**

1. 达成率 ＝ 成交金额 ÷ 目标，分子分母**同口径**：只统计「既有目标、又有实际」的日期。目标表覆盖 2026-10-01 ~ 11-30，但数据只到 11-02，因此 11-03 之后只有计划没有实际，一律不计入（`tgt.known()`）。
2. 目标表里没填的日子**不是目标 0**，而是「没有目标」，页面显示「无目标」，不会算出 0% 或 ∞。
3. 明细表按周/月汇总时，目标与分子都只取**该桶内的目标日**，避免拿整周成交去比只有几天的目标（否则达成率虚高）。
4. 官方目标配比是**按日总量固定权重拆分**：相对早班的比例为 数字人 0.50 / 中 0.87 / 晚 2.67（即 1 : 2 : 1.74 : 5.35），61 天里这三项比例的标准差分别为 0.011 / 0.052 / 0.267，说明是机械拆分而非逐日精算。落到结构上，晚班占目标约 68%。

**实测（2026-10-01 ~ 11-02，33 天有目标）**

| 班次 | 目标 | 实际 | 达成 |
|---|---|---|---|
| 数字人 | 38.1 万 | 26.0 万 | 68.3% |
| 早 | 74.6 万 | 67.6 万 | 90.6% |
| 中 | 62.9 万 | 176 万 | 279.2% |
| 晚 | 370 万 | 103 万 | 27.9% |
| **合计** | **545 万** | **372 万** | **68.3%** |

中班 279%、晚班 27.9% 这两个反常数字不是算错，是**目标挂错了班次**：10-20 当天目标整笔挂在晚班（晚 166.4 万、中 0、早 0、数字人 0.5 万），而当晚没有晚班场次，实际 133.8 万的大场发生在中班。剔除 10-20 后：中班 66.4%、晚班 50.8%、合计 62.9%——中班在没有离群场时反而略高于晚班，说明目标结构把晚班权重（约 68%）高估了。

## 主播效率对比矩阵

把主播按列、指标按行横向铺开，每格底色表示该指标在当行 7 人中的位置：

- **金色由浅到深**＝该指标越高；**红色由浅到深**＝退款越高；**灰底**＝中性行（总时长，只作参考，不判优劣）
- 行名后的 `↑ / ↓ / ·` 标明方向；该行最优格标 `★`
- 点任意行名可按该指标重排（再点一次反向），付款率这类「越低越好」的指标会自动用升序
- 悬停任一格显示：本项数值、全员数值、相对全员的百分比
- 「排行明细」页签保留原来的 12 列精确数值表格，用于核对具体数字

## 更新方式

源表换新后执行：

```bash
python build_data.py
```

如需指定路径：

```bash
python build_data.py --src "新的直播字段.xlsx" --sch "新的排班表.xlsx"
```

然后刷新页面即可，无需改任何前端代码。

> `data.js` 与 `data.json` 会同时生成。前者让页面可以直接双击打开，后者用于服务器/GitHub Pages。

更新线上版本：

```bash
git add -A
git commit -m "更新数据"
git push
```

推送后约 30–60 秒 GitHub Pages 自动重建，线上即生效。

## 指标口径

| 指标 | 公式 |
|---|---|
| 净销售 | 成交金额 − 退款金额 |
| 退款率 | 退款金额 ÷ 成交金额 |
| 单小时 GMV | 成交金额 ÷ 开播小时数 |
| 单小时 GSV | 净销售 ÷ 开播小时数 |
| 时均 UV | 观看人数 ÷ 开播小时数 |
| 客单价 | 成交金额 ÷ 成交人数 |
| 转化率 | 成交人数 ÷ 观看人数 |
| 加购率 | 加购人数 ÷ 观看人数 |
| 转粉率 | 新增粉丝数 ÷ 观看人数 |
| 曝光点击率 | 频道页点击人数 ÷ 频道页曝光人数 |
| **店铺发货金额** | 支付金额(全部) − 未发货仅退款 − 已收到货仅退款 − 在途仅退款 |
| **直播渗透率** | 当日直播成交金额 ÷ 当日店铺发货金额 |

所有比率均按「分子分母各自汇总后再相除」计算，**不是把每场比率取平均**，避免长短场次权重失真。

## 数据边界（重要）

1. **主播维度只覆盖 2026-10-01 ~ 2026-11-02（33 天 / 98 场）。** 因为排班表只提供 10-11 月。补更早的排班表后重跑脚本即可自动扩展，无需改代码。区间超出该范围时，主播页会提示覆盖率，不会把「无排班」显示成「业绩为 0」。
2. **数字人班次（00:00）无对应主播**，排班表只有早/中/晚三列，这是设计使然。
3. **数字人平均 12.9 小时/场，真人 4.4 小时/场**。两者单小时 GMV 不可直接比较，页面上已给出按时长归一的折算值（数字人等效约 ¥2,687/h，为真人 45%）。
4. **商品级数据按「商品 × 日」压缩存储**，因此品类与单品分析支持任意日期区间；订单明细（8,150 行 / 300 场 / 26 商品）样本不足，未做场次级商品结构分析。
5. **全店退款率 47.1%（全周期）、53.9%（近 90 天）显著偏高**。商品级支付合计与店铺日级支付合计偏差 0.00%，两个独立数据源互证通过，说明是数据本身如此，但对外引用前建议与天猫后台口径再复核。
6. 存在 29 场时长 <10 分钟、236 场 >12 小时（多为数字人挂机）的场次，已在数据中打 `flag` 标记，未做剔除。
7. **效率分布图对超大值做分位截断**：极少数单场（如 2026-10-20 中班单场 133.8 万）会把整张图压扁，因此坐标上限取 P95，超出部分钉在上边框、以虚线圈标示，并在图下注明个数与最高值，悬停可看真实值。
8. **活动名称来自官方节奏表，不是标题推断**。粒度是天，即「这一天属于哪档活动」，因此同一活动期内每场都一样；单场之间的差异（重点场 / 日常场）无法体现，也不该用标题去猜。日历覆盖 2025-01-01 ~ 2026-11-30，源表未覆盖到的日期若出现场次会落到「日销」，重跑时 `meta.rhythmMiss` 会报未匹配场次数（当前 0）。
9. **销售目标只有 2026-10-01 之后**。更早的区间一律显示「无目标」，不补造历史目标，也不拿 0 当目标。
10. **目标表里 10-20 的目标挂错班次**：晚 166.4 万、中 0，而当天没有晚班场次、大场在中班（133.8 万）。这是源表本身的问题，页面照实呈现，未做人工调整；剔除该日后中班 66.4%、晚班 50.8%。

## 校验记录

- 场次表 1,795 场，19 个月连续，成交金额 0 空值
- 平台比率自洽：用 GMV/退款重算退款率，1,192 场偏差 >1pct 的 0 场
- 商品级支付合计 = 店铺日级支付合计，偏差 0.00%
- 排班匹配：排班区间内 131 场，98 场真人全部匹配成功，未匹配数 0
- 活动节奏匹配：1,795 场 × 官方日历逐日比对，未匹配 0 场；日历 699 天（2025 全年 + 2026-01-01~11-30），归一后 32 个节奏名
- 销售目标：61 天（2026-10-01~11-30），其中 33 天有实际；目标合计 545 万 / 实际 372 万 / 达成 68.3%，与独立用 openpyxl + 原始场次重算结果逐位一致
- 前端实测：Chromium 实际渲染，4 页面 × 3 种宽度（1440 / 1180 / 820）× 多组区间切换，JS 错误 0、横向滚动 0、文字溢出 0
